一、同步等待和其他 CPU

同步等待 = cudaDeviceSynchronize + cudaEventSynchronize + cudaStreamSynchronize + cudaStreamWaitEvent 的 Self CPU。其他 CPU = Self CPU 总量 − 同步等待。cudaGraphLaunch 和 cudaLaunchKernel 算在其他 CPU 里。四卡平均。Intel 只有未绑核的一次：4 实例，只 profile 了 instance0。

同步在左缘结束。GPU 跑 GEMM 时，CPU 在跑 host 代码，不等这次 GEMM。竖线是 cudaLaunchKernel，每次 7.8 µs。

  • CPU 先发射 CUDA Graph：cudaGraphLaunch 约 93.6 µs，记在其他 CPU。
  • 立即进入 cudaDeviceSynchronize，约 21.49 ms，等 GPU 上的 CUDA Graph 回放结束。这一段记在同步等待。
  • 同步返回后，GPU 跑 GEMM 621 µs、AllGather 203 µs、argmax 319 µs。这些 kernel 的时间记在 Self CUDA，不在同步等待那一列。
  • GEMM 运行期间，CPU 不在等这次 GEMM。rank0 的 trace 里 617 µs 中大约 573 µs 没有 CUDA 调用，CPU 在跑 host 代码，记在其他 CPU。中间穿插的 cudaLaunchKernel 每次约 5–8 µs，用来发射后面的 AllGather 和 argmax。
  • argmax 之后，CPU 通过 cudaEventSynchronize 拿到 token，单次约 18 µs。

三、绑核后同步等待的提升幅度为什么不一样

同步等待的提升幅度，鲲鹏是 0.36%（少 0.320 s），海光是 0.22%（少 0.199 s）。差在两处：鲲鹏少做了 9 次 CUDA Graph，海光一次没少；单次等待的四卡平均海光降得更多，但那是各 rank 之间此消彼长，不是每张卡的图都变短了。

鲲鹏总量提升更大，是因为少了 9 次不满 batch 的图回放，约 0.194 s。海光单次平均降得更多，主要是 rank0 少等 438 µs、rank1 多等 262 µs，等待在卡之间搬家。一步的墙钟看最慢的那张卡，不跟着这个平均值少。cudaGraphLaunch 和 cudaLaunchKernel 的单次耗时在其他 CPU 里，不解释这两列同步等待的差。

六、为什么这两处再往下压不动

少掉的 9 次图，是不满 batch 的 decode 步并进了 bs8。绑核之后稳态已经是一步一次 CUDA Graph，4096 次，和生成的 token 步一一对应。再少一次图，就是少生成一步，不是把同一步的发射省掉。海光两次都是 4096 次，没有这 9 步可以再减。prefill 那些 100 ms 级的步走 eager，不在这 9 次里面。

单次等待的 28 µs 和 47 µs 是四张卡平均出来的。rank0 少等的时候，rank1、rank2 在多等。一步要等最慢的那张卡，平均值下来并不缩短这一步。把 rank0 再推迟到和别的 rank 一起进图，只是把等待从一张卡记到另一张卡上，最慢的那张卡还是那么慢。图本体大约 21.5 ms，绑核能搬动的只有这几十微秒。鲲鹏绑核后单次已经是 21.49 ms，海光是 21.84 ms。

cudaGraphLaunch 和 cudaLaunchKernel 属于其他 CPU，不在同步等待里。鲲鹏绑核后两项合计 0.766 s。次数这边，稳态 GraphLaunch 已经是一步一次，4096 次，再少就是少生成一步；LaunchKernel 多出来的那几百次是图外 eager，海光绑核少发过 901 次，端到端没有变快。单次时间这边，鲲鹏 GraphLaunch 约 94 µs、LaunchKernel 约 8 µs，绑核后已经从 107 µs 降到 94 µs；海光约 76 µs，绑核后反而略升。这份数据里看不到再往下压的空间。
